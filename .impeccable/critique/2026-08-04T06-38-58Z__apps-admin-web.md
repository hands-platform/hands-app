## Design Specificity Verdict

The operational data is specific to HANDS, but the interface structure is category-interchangeable Vuexy dashboard composition. HANDS-specific concepts—matching, customer choice, partner travel, service completion, cash debt, refund decisions, and shift handoff—do not form one consistent queue-to-case-to-decision workflow.

## Overall Impression

The admin has a useful functional foundation, but it answers “what features and numbers exist” more readily than “what exact case should I handle next, why, by when, and with what evidence.” The biggest opportunity is a shared operator queue contract and a guarded case-decision layout, not a new visual library.

## What's Working

- SLA, age, amount, and queue counts are already available in many core views.
- Refund and notification copy contains evidence-first operating rules that can become structured decision guards.
- Shared shell, page template, navigation, metric, queue, filter, and form components make systemic fixes possible without a rewrite.

## Priority Issues

### [P1] Risky state changes precede the evidence decision

- **Why it matters**: Equal-weight booking checkpoint actions and the exposed no-show form can create customer, partner, and financial consequences from a premature click.
- **Fix**: Use one recommended action, checklist rows, required block/reopen reasons, evidence summary, permission check, and audit trail. Put no-show inside a mutually exclusive cannot-complete-service flow.
- **Suggested command**: `$impeccable harden`

### [P1] Live queues mix stale, test, and current operational data

- **Why it matters**: 19/46-day live bookings, 75-day notification failures, and Demo/Smoke records train operators to distrust urgency signals.
- **Fix**: Enforce live time bounds, quarantine stale active records, hide test data by default, and show freshness/time-scope metadata.
- **Suggested command**: `$impeccable clarify`

### [P1] Navigation reflects implementation breadth, not operator roles

- **Why it matters**: 11 sections and 62 links make daily work compete with records, monthly close, restricted settings, and developer tools.
- **Fix**: Limit first-level navigation to Shift command, Live service, Support cases, Partner review, Money actions, and Handoff; move the rest under Records & settings and set role defaults.
- **Suggested command**: `$impeccable distill`

### [P2] Pages describe queues but do not assign an actionable next step

- **Why it matters**: Generic actions such as Resolve overdue and long Ops hint paragraphs make operators reinterpret the process for every case.
- **Fix**: Standardize priority, case, next action, owner, assignee, SLA, last action, and impact; use short verbs and side-panel detail.
- **Suggested command**: `$impeccable clarify`

### [P2] The shared shell repeats titles and permanent chrome

- **Why it matters**: Breadcrumb, page title, H1, theme controls, location, workspace chip, and policy/help controls displace primary work.
- **Fix**: Keep one page title, one theme control, contextual help, a real data-freshness status, and an accessible notification label.
- **Suggested command**: `$impeccable layout`

## Persona Red Flags

**Alex — experienced operator**: Ctrl K finds destinations but not My queue, recent cases, or assignments. Opening the oldest refund still requires dashboard, queue, filters, row, booking, and payment context. Empty approval queues retain the full filter matrix.

**Jordan — new operator**: Start Shift, Operations History, and Handoff do not form a clear model. FCM_HTTP_V1, ledger, closeout, MATCHED, and PENDING appear before plain next actions. Uniform red urgency cards and Resolve overdue do not establish the first safe action.

**Sam — keyboard/screen-reader operator**: The notification icon button has no accessible name in the DOM. Duplicate breadcrumb/title/H1 and very long table rows increase linear reading cost. Desktop-only gating plus wide tables makes 200% zoom difficult.

- Notification technical incidents are mixed into Customer Support.
